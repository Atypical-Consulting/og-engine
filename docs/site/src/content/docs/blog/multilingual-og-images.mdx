If your product serves users who write in Japanese, Arabic, Chinese or Korean, your OG image generator probably has bugs you haven't noticed yet. One up-front caveat before we start: OG Engine does not render emoji glyphs. If your titles contain emoji, read [Emoji: measured correctly, not drawn](#emoji-measured-correctly-not-drawn) first.

## The Problem

Most OG image solutions use one of two approaches:

1. **HTML/CSS in headless Chrome** — works for all scripts, but costs 850ms and 200MB per render
2. **Simple Canvas text drawing** — fast, but breaks on:
   - CJK line wrapping (breaks mid-word or at wrong characters)
   - Arabic bidirectional text (renders backwards or disconnects letter forms)
   - Emoji sequences (splits multi-codepoint emoji into broken symbols)
   - Mixed scripts (Japanese + English in one title)

OG Engine gets the CJK, Arabic and mixed-script cases right, because it uses Pretext for text segmentation rather than naive string splitting. It gets emoji *segmentation* right for the same reason — but it has no emoji font to draw with, so the glyph itself comes out as an empty box. That limitation is detailed below.

## CJK: Chinese, Japanese, Korean

CJK text doesn't use spaces between words. Line breaking follows specific rules:

- **Can break** between most CJK characters
- **Cannot break** before punctuation like `。`, `、`, `)`, `」`
- **Cannot break** after opening punctuation like `(`, `「`
- **Mixed text** (CJK + Latin) requires break opportunities at script boundaries

OG Engine ships with **Noto Sans JP** pre-loaded, covering all CJK Unified Ideographs, Hiragana, and Katakana.

### Example

```json
{
  "format": "og",
  "title": "サーバーサイドの画像生成 — ブラウザ不要",
  "description": "Pretextエンジンによる高速テキストレイアウト。2msでPNG生成。",
  "style": { "font": "Noto Sans JP" }
}
```

## Arabic: Bidirectional Text

Arabic text is right-to-left (RTL), but numbers and Latin text within Arabic are left-to-right. This creates bidirectional runs that must be reordered for display.

Additionally, Arabic letters change shape based on position:

- **Isolated:** ع
- **Initial:** عـ
- **Medial:** ـعـ
- **Final:** ـع

Pretext handles the Unicode Bidirectional Algorithm (UAX #9), and the font shaping is handled by the Canvas text renderer (Skia via @napi-rs/canvas).

OG Engine ships with **Noto Sans Arabic** pre-loaded.

### Example

```json
{
  "format": "og",
  "title": "إنشاء صور OG بدون متصفح",
  "description": "محرك تخطيط النص بدون Chrome — 2 مللي ثانية لكل صورة",
  "style": { "font": "Noto Sans Arabic" }
}
```

## Emoji: measured correctly, not drawn

This is the one case OG Engine does not handle today, and it is worth being precise about where the line falls.

Modern emoji are surprisingly complex:

- Flag emoji: 🇫🇷 = two regional indicator symbols
- Skin tone: 👋🏽 = hand + skin tone modifier
- Family: 👨‍👩‍👧‍👦 = four people joined by zero-width joiners (7 codepoints, 1 glyph)
- Compound: ❤️‍🔥 = heart + ZWJ + fire

Naive string operations (like `str.length` or `str.slice()`) break these sequences. Pretext uses grapheme cluster segmentation (UAX #29) to treat each visual emoji as a single unit for line breaking and measurement — so the *layout* is right: a family emoji counts as one cluster, not seven, and a line never breaks in the middle of a ZWJ sequence.

What is missing is the glyph. None of OG Engine's pre-loaded font families is an emoji face, and there is no option to supply one, so an emoji in your text renders as an empty box (`▯`) — "tofu". A title like `Ship Features, Not Browsers 🚀` comes back with the rocket drawn as `▯`, at the correct width, in the correct position.

So the practical guidance is: keep emoji out of OG Engine titles and descriptions for now. If emoji are essential to your cards, a Satori-based renderer with its `graphemeImages` escape hatch, or a headless browser, will do what OG Engine cannot — see [OG Engine vs Satori](/compare/satori/).

## Mixed Script Content

Real-world titles mix scripts: "新機能: OG Engine v0.2 リリース" contains Japanese, Latin, numbers, and punctuation. Pretext handles script boundary detection and applies appropriate break rules for each segment.
